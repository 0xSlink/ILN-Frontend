# Internationalization (i18n)

See the [consolidated i18n readiness report](i18n-readiness-report.md) for the category close-out, including the hardcoded-string audit, dependency decision, RTL assessment, CI parity gate, and locale roadmap.

## Current architecture

The frontend currently uses the i18next stack directly:

- [src/i18n.ts](../src/i18n.ts) bootstraps i18next, react-i18next, and the browser language detector.
- [src/components/I18nProvider.tsx](../src/components/I18nProvider.tsx) wraps the app with the I18next provider.
- Translation files live under [public/locales](../public/locales) as JSON bundles, with the active locales currently being English and Spanish.

The repository also declares `next-intl` in the package manifest, but the codebase does not currently import or initialize it. In practice, the app is using the i18next family for runtime translations, so `next-intl` should be treated as a leftover dependency unless a migration is explicitly planned.

## Translation file layout

Each locale has a translation bundle in the matching folder under [public/locales](../public/locales):

- [public/locales/en/translation.json](../public/locales/en/translation.json)
- [public/locales/es/translation.json](../public/locales/es/translation.json)

The JSON structure is namespaced by feature (for example `common`, `nav`, `landing`, and `submitForm`), which keeps translations organized as the UI grows.

## How to add a new locale

1. Create a new locale folder under [public/locales](../public/locales), for example `public/locales/fr/`.
2. Copy [public/locales/en/translation.json](../public/locales/en/translation.json) into the new folder and translate the values.
3. Update [src/i18n.ts](../src/i18n.ts) to include the new locale in the resource map and the supported language list.
4. If the locale should be selected automatically, ensure the new language code is compatible with the browser language detector settings in [src/i18n.ts](../src/i18n.ts).
5. Run `pnpm run i18n:check`. It lists every key the new locale is missing or has in addition to `en`, and CI runs the same check.
6. Run the app and verify the new locale loads in the browser. If the new locale is meant to be visible in the UI, add a fallback or an explicit switcher entry where needed.

### Example change

```ts
const resources = {
  en: { translation: en },
  es: { translation: es },
  fr: { translation: fr },
};

fallbackLng: 'en',
supportedLngs: ['en', 'es', 'fr'],
```

## Locale scope decision

The two active locales (`en` and `es`) share the same keys, grouped under `common`, `nav`, `landing`, `footer`, `submitForm`, `freelancer`, `lpDashboard`, and `language`. This is enforced in CI rather than verified by hand: `pnpm run i18n:check` ([scripts/check-locale-parity.mjs](../scripts/check-locale-parity.mjs)) compares every locale's full set of nested keys (for example `nav.howItWorks`, not just `nav`) with `en` and fails the CI `lint` job on any missing or extra key. It also runs as part of `pnpm run verify`.

Formatting utilities (`src/lib/formatting.ts`, `src/hooks/useLocaleFormatting.ts`) already accept a `locale` parameter from the i18n context. The legacy helpers in `src/utils/format.ts` and `src/utils/invoiceSubmission.ts` previously hardcoded `'en-US'` and now accept an optional `locale` parameter (defaulting to `'en-US'` for backward compatibility).

Future locales should:
- Mirror the full key set from `en/translation.json` (enforced by `pnpm run i18n:check`)
- Be added to `supportedLngs` in `src/i18n.ts`
- Include a `language.<code>` entry for the language switcher

## Maintainer note

If the team wants a single canonical i18n solution, the current evidence points to consolidating around i18next/react-i18next and removing or deprecating `next-intl` rather than maintaining both in parallel.

## RTL-readiness assessment

Neither `en` nor `es` is RTL, but the layout is not currently safe for RTL without work.

Key findings:
- Layout relies on physical `left`/`right` positioning in several components, including `ActivityHeatmap.tsx`, `ErrorBoundary.tsx`, `Spotlight.tsx`, `VotingProgressBar.tsx`, and chart margins in multiple `src/components/charts/*.tsx` files.
- Several UI pieces use physical directional utilities such as `ml-*`, `mr-*`, `pl-*`, `pr-*`, `left-*`, and `right-*` across the component tree.
- `next-intl` is present in the manifest but unused; adding an RTL locale would also require migrating away from the current i18next setup if we want built-in RTL helpers.

Current status: **not tested, likely needs work** for RTL.

Scoped follow-up recommended:
- Audit `left`/`right` usages in `src/components/**` and `src/app/**`.
- Replace obvious layout spacing with logical properties where practical.
- Add `[dir="rtl"]` coverage to visual regression and smoke tests before enabling an RTL locale.

## Locale expansion plan

This plan turns the generic guidance above into concrete steps for the next locale ahead of mainnet.

### Choosing the next locale

The repository has no data yet on where users are. The frontend has no usage analytics (Sentry only tracks errors), so the next locale is chosen by these criteria rather than guessed:

1. **Target market.** The product owner confirms a launch or partner market for mainnet (for example, a payer or freelancer pilot) whose primary language `en` and `es` do not cover.
2. **Measured demand.** Once aggregate, anonymous browser-language counts are collected (the i18next language detector already reads `navigator.languages`), a language that makes up at least 5% of sessions over 30 days qualifies.
3. **Translation owner.** A native speaker has agreed to own the locale (see below). A locale is never added without one.
4. **Script direction.** Left-to-right locales come first. Right-to-left locales wait until the RTL work in the assessment above is done and the next-intl question is settled.

The highest-scoring candidate on these criteria is the next locale. Record the decision and its reasoning in this section when it is made.

### When to add it

Start work when both of these are true:

- the candidate meets criterion 1 or 2
- a translation owner is named (criterion 3)

### Who owns translation quality

- Each locale has a named translation owner, a native speaker who writes or reviews every string for that locale.
- A second native speaker reviews the initial translation before it ships.
- When the locale is added, give the owner a `CODEOWNERS` entry for `public/locales/<code>/` so their review is requested automatically. The maintainers in `CODEOWNERS` keep final sign-off.

### Adding it

1. Follow [How to add a new locale](#how-to-add-a-new-locale) above.
2. `pnpm run i18n:check` is the quality gate. The PR cannot pass CI until the new locale has exactly the same keys as `en`.
3. Check the locale in the browser, including number and date formatting through `useLocaleFormatting`, before asking the translation owner for review.

### Keeping it complete

- Every PR that adds an English string adds the same key to every locale, which `pnpm run i18n:check` enforces.
- If a translation is not ready, use the English text as a placeholder, tag the translation owner in the PR, and open a follow-up issue to translate it.
