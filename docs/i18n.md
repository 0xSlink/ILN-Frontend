# Internationalization (i18n)

## Current architecture

The frontend currently uses the i18next stack directly:

- [src/i18n.ts](../src/i18n.ts) bootstraps i18next, react-i18next, and the browser language detector.
- [src/components/I18nProvider.tsx](../src/components/I18nProvider.tsx) wraps the app with the I18next provider.
- Translation files live under [public/locales](../public/locales) as JSON bundles, with the active locales currently being English and Spanish.

The repository also declares `next-intl` in the package manifest, but the codebase does not currently import or initialize it. In practice, the app is using the i18next family for runtime translations, so `next-intl` should be treated as a leftover dependency unless a migration is explicitly planned.

## Translation file layout

Each locale has a translation bundle in the matching folder under [public/locales](../public/locales):

- [public/locales/en/translation.json](../public/locales/en/translation.json)
- [public/locales/es/translation.json](../public/locales/es/translation.json)

The JSON structure is namespaced by feature (for example `common`, `nav`, `landing`, and `submitForm`), which keeps translations organized as the UI grows.

## How to add a new locale

1. Create a new locale folder under [public/locales](../public/locales), for example `public/locales/fr/`.
2. Copy [public/locales/en/translation.json](../public/locales/en/translation.json) into the new folder and translate the values.
3. Update [src/i18n.ts](../src/i18n.ts) to include the new locale in the resource map and the supported language list.
4. If the locale should be selected automatically, ensure the new language code is compatible with the browser language detector settings in [src/i18n.ts](../src/i18n.ts).
5. Run the app and verify the new locale loads in the browser. If the new locale is meant to be visible in the UI, add a fallback or an explicit switcher entry where needed.

### Example change

```ts
const resources = {
  en: { translation: en },
  es: { translation: es },
  fr: { translation: fr },
};

fallbackLng: 'en',
supportedLngs: ['en', 'es', 'fr'],
```

## Maintainer note

If the team wants a single canonical i18n solution, the current evidence points to consolidating around i18next/react-i18next and removing or deprecating `next-intl` rather than maintaining both in parallel.
